# ADR-20260812-008 — Deterministic validation runs outside the agent

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-SAFE-005, REQ-AGT-002, REQ-AGT-004, REQ-VAL-001

## Context

The slice needs several checks that must never be wrong: the output matches its
schema, every section resolves to an approved source reference, all safety
assertions hold, and the correlation identifier was echoed unchanged.

The agent could perform these checks on itself. It should not. A component
asserting its own compliance is not evidence, and a generation that has drifted
is exactly the generation least able to notice. The design review also raised
reproducibility: without a pinned instruction version, two runs of the same input
cannot be compared, and a regression cannot be attributed.

## Decision

All deterministic validation runs outside the agent, in the orchestration layer,
after the agent returns and before anything reaches a human.

The order is fixed and every step fails closed:

1. Output schema validation — `E-OUTPUT-SCHEMA-INVALID`
2. Safety assertion check, all nine `safetyStatus` fields —`E-SAFETY-FLAG`
3. Grounding resolution, every section reference resolves into the approved
   bundle — `E-GROUNDING-FAILURE`
4. Correlation echo check — fail closed on mismatch

Reproducibility rests on values the orchestration layer controls, not on
platform metadata that cannot be verified from the payload:
`provenance.agentInstructionVersion` and `provenance.agentInstructionSha256`,
computed over a versioned instruction file held in the repository.

The `safetyStatus` block remains in the payload. It is the agent's assertion, and
it is useful precisely because it is checked by something else. The payload
assertion and the external check are two independent controls, and both must
agree.

`safetyStatus.externalRetrievalDisabled` is an assertion the agent cannot prove
about its own deployment. It is retained as an intent marker, and the actual
control is a deployment-configuration check tracked in `docs/risks.md`.

## Alternatives

- **Agent self-validation via instructions.** Rejected. It produces no evidence
  and fails in correlated ways with the generation itself.
- **Validate only at the user interface layer.** Rejected. Content would reach a
  rendering path before the grounding check, and a rendering bug becomes a
  safety bug.
- **Trust platform-reported model and version metadata for reproducibility.**
  Rejected. The field set and stability are not verified for this path, and the
  charter prohibits representing unverified platform behavior as operational.
- **Warn rather than block on partial grounding.** Rejected.
  `groundingCoverageRatio` is pinned to `1`; partial grounding is a refusal.

## Consequences

- The orchestration layer owns a shared validation utility used by both the
  generation path and the approval path, so the two cannot diverge.
- One place to change a rule, and one place to read to know what is enforced.
- A small latency cost per run. Accepted.
- Agent instructions must be versioned files in the repository, not console-only
  configuration, so the digest is meaningful.

## Healthcare, privacy, security, and data impact

Positive. No unvalidated generated content reaches a human. Refusal is the
default outcome for every check, so a partially correct draft is never presented
as complete. Reproducibility means a safety regression can be attributed to a
specific instruction version rather than argued about.

## Validation evidence

`node scripts/validate-contracts.mjs` — cross-field rules `source-reference-resolution`,
`bundle-binding`, `artifact-binding`, and `correlation-propagation` implement the
external checks over the example set. Fixtures
`agent-output-ungrounded-open-item.json` and `agent-output-safety-flag-false.json`
are refused. `provenance.agentInstructionSha256` is required and pattern-checked
in `contracts/schemas/shift-closeout-agent-output.schema.json`.

`node src/governance/test/run-governance-checks.mjs` — 31 of 31 checks pass,
exit code 0. Since the 2026-08-12 integration, `src/orchestration/output-validator.mjs`,
`audit-adapter.mjs`, `approval-orchestrator.mjs`, and `input-builder.mjs` call
these governance modules directly, so the single validation layer this decision
requires is one implementation rather than two that agree by inspection.
