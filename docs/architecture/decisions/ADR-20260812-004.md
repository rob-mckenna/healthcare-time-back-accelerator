# ADR-20260812-004 — Draft label, lifecycle status, and safety status stay separate

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-SAFE-001, REQ-APPR-001, REQ-SAFE-002, REQ-WF-003

## Context

Three different questions are asked about a generated artifact, and it is
tempting to answer all three with one `status` field:

1. Is this machine-generated content that a human must read? (Always yes.)
2. Where is it in the human review path? (Draft, approved, rejected, revision.)
3. Did the generation respect the clinical and data boundaries? (Nine assertions.)

Collapsing them means an approval transition also mutates the draft label, and
the artifact stops announcing that it was machine-generated at the exact moment
someone is most likely to act on it.

## Decision

Three separate fields, defined in `docs/conventions/draft-and-safety-status.md`:

**`draftStatus`** is a `const` equal to `DRAFT — HUMAN REVIEW REQUIRED`
(em dash, U+2014). It is immutable, non-overridable by configuration, and it does
not change after approval. An approved artifact is a draft a human accepted, not
a signed document.

**`lifecycleStatus`** carries the review position: `DRAFT`,
`APPROVED-SIMULATED`, `REJECTED`, `REVISION-REQUESTED`. The agent output schema
pins it to `DRAFT` with a `const`, so the agent cannot emit an approved
artifact. Only an approval event moves it.

The approved value is named `APPROVED-SIMULATED` rather than `APPROVED` because
nothing is signed, nothing is written to a system of record, and nothing leaves
the prototype. The suffix keeps that visible in evidence and in demonstrations.

**`safetyStatus`** carries nine machine-checkable assertions about the content,
eight pinned to `true` and `groundingCoverageRatio` pinned to `1`.

## Alternatives

- **One `status` enum.** Rejected. Approval would erase the draft label.
- **Draft label as a rendering concern only.** Rejected. Exported or copied text
  would lose it, which is precisely when it matters.
- **Name the approved state `APPROVED`.** Rejected. It reads as a production
  clinical approval in screenshots and evidence exports.
- **`safetyStatus` as a score or confidence value.** Rejected. A threshold
  invites a judgement call at the boundary; a `const` does not.

## Consequences

- Any surface that renders the artifact must render the label, and a surface that
  cannot render it does not render the artifact.
- Evidence records three orthogonal facts, so a reviewer can distinguish "a human
  accepted this" from "this is safe machine output".
- Slightly more verbose payloads. Accepted.

## Healthcare, privacy, security, and data impact

Positive. The artifact never stops announcing that it is machine-generated
content requiring human review, including in exports, screenshots, and after
acceptance. The approved state cannot be mistaken for a clinical signature.

## Validation evidence

`node scripts/validate-contracts.mjs` — fixtures
`agent-output-missing-draft-status.json`,
`agent-output-self-approved-lifecycle.json`, and
`agent-output-safety-flag-false.json` are each refused for their recorded
reason. The approval-event schema's `allOf` conditionals assert that each
decision produces the matching `lifecycleStatus` and status label.

`node scripts/run-local-journey.mjs` — the 2026-08-12 run confirmed the label is
present on the rendered draft and unchanged after approval, and that
`src/view/draft-view.mjs` refuses to render an artifact whose label or
`lifecycleStatus` has been altered.
