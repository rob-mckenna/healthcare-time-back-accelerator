# ADR-20260812-009 — Fail-closed markers are structural constants

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-SAFE-005, REQ-WF-001, REQ-WF-002, REQ-DATA-004, REQ-AUD-003

## Context

The charter requires failing closed on missing identity, unconfirmed context,
schema invalidity, grounding failure, and missing approval. The usual
implementation is a boolean plus a runtime check: `if (!authenticated) throw`.

That pattern has a defect that matters here. The unsafe state is fully
representable, so an unauthenticated request is a valid object that merely
happens to be rejected by a check that someone can move, reorder, or skip while
debugging a demonstration. The object itself never objects.

## Decision

Where a value has exactly one safe state, the schema pins it with `const`. The
unsafe state stops being representable rather than being caught.

| Field | Constant | Effect |
|---|---|---|
| `requester.authenticated` | `true` | An unauthenticated request is not a valid input |
| `sourceBundle.approvedForGeneration` | `true` | An unapproved bundle cannot be submitted |
| `data.syntheticOnly` | `true` | A non-synthetic pack is not a valid configuration |
| `safetyStatus.*` (eight booleans) | `true` | A failed safety assertion is not a valid output |
| `safetyStatus.groundingCoverageRatio` | `1` | Partial grounding is not a valid output |
| `output.lifecycleStatus` | `"DRAFT"` | The agent cannot emit an approved artifact |
| `draftStatus` | `"DRAFT — HUMAN REVIEW REQUIRED"` | The label cannot be replaced |
| `decisionReasonScanned` | `true` | Unscanned human free text cannot be recorded |
| `revisionInstructionsSanitized` | `true` | Unsanitized revision text cannot be submitted |

Timestamp gates use required properties rather than constants, because their
value is genuinely variable: `context.preGenerationConfirmedAt` and
`reconfirmedContext.preApprovalConfirmedAt` are required, and the cross-field
rule `context-reconfirmation-match` asserts the two confirmations refer to the
same patient and encounter.

Conditional requirements cover the states that only apply sometimes: an audit
event with outcome `FAILED` or `BLOCKED` requires a `failClosedCode`; a rejected
or revision-requested approval requires a reason.

The two `…Scanned` and `…Sanitized` markers are deliberately named as claims
about work already performed. The work itself lives in the shared validation
utility described in ADR-20260812-008; the constant makes it impossible to record
the event without having run it.

## Alternatives

- **Optional booleans with runtime checks.** Rejected. The unsafe object stays
  valid and the check is movable.
- **Enumerations such as `authState: authenticated | anonymous`.** Rejected. It
  models a state the system must never accept as if it were a supported case.
- **Omit the flags and infer safety from context.** Rejected. Nothing would be
  assertable by a validator, so no evidence could be produced.

## Consequences

- Eighteen negative fixtures produce concrete refusal evidence for the safety
  gates rather than a claim that checks exist.
- Payloads carry fields whose value is always the same, which looks redundant
  until one considers what their absence would permit.
- Adding a new gate means adding a constant and a fixture together, which keeps
  the evidence set complete by construction.

## Healthcare, privacy, security, and data impact

Positive. Every charter fail-closed condition is enforced at the boundary rather
than by a check that can be bypassed under demonstration pressure. Audit
evidence is guaranteed to name the failure condition, so a blocked run is
distinguishable from a run that never happened.

## Validation evidence

`node scripts/validate-contracts.mjs` — 19 negative fixtures under
`contracts/examples/invalid/`, each asserted to be refused for its recorded
reason, including `agent-input-unauthenticated-requester.json`,
`agent-input-unapproved-source-bundle.json`,
`agent-input-missing-context-confirmation.json`,
`organization-config-non-synthetic-data.json`, and
`audit-event-blocked-without-code.json`. 48 of 48 checks pass, exit code 0.

`node src/orchestration/test/run-fail-closed-catalog.mjs` — 38 of 38 checks
pass, exit code 0: every one of the twelve fail-closed codes is produced by a
real refusal and mapped to a configured user-safe message
(2026-08-12 integration run).
