# ADR-20260812-010 — Deferred capabilities appear only as FUTURE

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-SCOPE-008, REQ-SAFE-003, REQ-SAFE-006, REQ-STORY-002, REQ-STORY-003

## Context

The charter defers a large set of capabilities out of P0: live system-of-record
integration, additional agents and workflows, multi-tenant onboarding at scale,
production connectors, and real measurement of outcomes. Two pressures push
against that boundary. A demonstration is more impressive with a stub that looks
like an integration. A document is more persuasive when a deferred item is
written in the present tense.

Both produce the same failure: an audience, or a future implementer, believes
something operates that does not exist. In a healthcare context that belief is
not merely embarrassing.

## Decision

A deferred capability may appear in documentation, marked `FUTURE`, with an
explicit statement that it is not implemented. It may not appear as a stub, a
mock endpoint, a placeholder screen, a disabled control that implies a working
feature, or a configuration key reserved for it.

Three concrete rules:

1. **No stubs for deferred systems.** If a system-of-record write is out of
   scope, there is no write path, no mock writer, and no `TODO` client. The
   `APPROVED-SIMULATED` lifecycle value exists precisely so acceptance can be
   recorded without implying a write.
2. **`FUTURE` markers are prose-only.** They live in documentation. They do not
   appear as code paths, feature flags, or reserved configuration keys, because
   a reserved key invites someone to populate it.
3. **Present tense is reserved for what runs.** Documentation describes deferred
   capability with explicit future or conditional framing, and the prohibited
   claim list in `docs/conventions/prohibited-claims.json` blocks the specific
   phrasings that assert a status this prototype does not have.

The same rule governs unverified platform behavior. Where a Microsoft product
capability has not been verified in this environment, it is recorded as an
assumption in `docs/assumptions.md` or a blocker in `docs/risks.md`, never
described as working.

## Alternatives

- **Build thin stubs to show the shape of the full solution.** Rejected. A stub
  that renders convincingly is indistinguishable from an implementation in a
  demonstration, which is the entire risk.
- **Mark deferred items `TODO` in code.** Rejected. `TODO` markers accumulate,
  get partially implemented, and become the pretend-integration this decision
  exists to prevent.
- **Leave the boundary to reviewer judgement.** Rejected. Scope pressure lands
  hardest exactly when review capacity is lowest.

## Consequences

- The demonstration is smaller and entirely honest. Every element on screen is
  backed by something that ran.
- Extension after P0 starts from a clean boundary rather than from stubs of
  unknown fidelity.
- Some conversations require explaining what is deliberately absent. That
  explanation is a feature of a bounded plan, not an apology for it.

## Healthcare, privacy, security, and data impact

Positive. It removes the risk that a clinical or executive audience believes a
draft was written to a record, communicated to a patient, or validated against
real outcomes. It also keeps the illustrative time-back figures clearly separated
from measured results.

## Validation evidence

`node scripts/validate-docs.mjs` — scans every Markdown file against the
prohibited claim list in `docs/conventions/prohibited-claims.json` and asserts
that any document presenting time-back figures also carries the `ILLUSTRATIVE`
label. Exit code 0. The repository contains no stub or mock client for any
deferred system; the tracked file set is contracts, configuration, documentation,
and validation scripts only.

## Supersedes

None.
