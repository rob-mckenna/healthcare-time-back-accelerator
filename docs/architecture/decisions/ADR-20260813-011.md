# ADR-20260813-011 — Use the direct Copilot Studio connected-agent path

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-SCOPE-001, REQ-SCOPE-002, REQ-WF-003, REQ-SAFE-006

## Context

The P0 architecture needs a supported path from the single Copilot Studio
experience to the single Microsoft Foundry Shift Closeout Agent. The original
BLOCKER-001 register recommended a Power Automate proxy because the direct
product path had not been established.

Microsoft Learn now documents a preview path in Copilot Studio:
**Agents → Add an agent → Connect to an external agent → Microsoft Foundry**.
The documented setup uses a connection created with a Foundry project endpoint,
then Name, Description, and Agent Id. Only agents created in the new Microsoft
Foundry portal are supported by this path.

The Learn page does not define this accelerator's JSON input/output contract,
timeout semantics, error taxonomy, or end-user identity and role-claim
propagation. Those remain accelerator responsibilities and require separate
validation.

## Decision

Use the documented direct Microsoft Foundry connected-agent path for P0. Do not
place a Power Automate proxy in the target invocation path.

The decision establishes the product binding only:

1. Configure the connection with the environment-supplied Foundry project
   endpoint and Agent Id.
2. Treat the feature as preview and standard-harness powered.
3. Use only the single new-portal Foundry Shift Closeout Agent.
4. Keep authentication, authorization, context confirmation, deterministic
   output validation, human approval, and audit controls outside the connection.
5. Do not claim that the connector natively transports or enforces the
   repository's structured contracts. A live Copilot Studio test must establish
   the actual request and response adaptation before the binding is accepted as
   operational.

BLOCKER-001's invocation-path decision is resolved by this ADR. Direct
connected-agent validation remains **NOT RUN** and is tracked independently of
the completed Foundry-agent provisioning and evaluation work in issue #6.

## Alternatives

- **Power Automate proxy.** Rejected for the P0 target path because Microsoft
  documents a direct connected-agent path and the human owner selected it.
- **Validation harness only.** Retained as the local simulation and contract
  test boundary, but it does not satisfy the Copilot Studio binding.

## Consequences

- The target architecture has one direct Copilot Studio-to-Foundry connection
  and no proxy component.
- The architecture is simpler, but the preview feature remains an explicit
  platform dependency.
- The repository contract is an accelerator requirement, not a documented
  connector guarantee. A tested adapter may be required in the authored topic.
- Live Foundry agent evaluation evidence does not constitute live Copilot Studio
  connected-agent evidence.

## Healthcare, privacy, security, and data impact

The connection does not weaken the synthetic-only, minimum-necessary,
draft-only, fail-closed, or human-approval boundaries. No end-user identity,
authorization, or role propagation is assumed. No system-of-record write or
clinical action is introduced.

## Validation evidence

- Official source reviewed 2026-08-13:
  [Connect to a Microsoft Foundry agent (preview)](https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-agent-foundry-agent).
- Documentation and local contract validation: `npm run verify`.
- Direct Copilot Studio connected-agent validation: **NOT RUN**.

## Supersedes

The BLOCKER-001 Power Automate recommendation in the original risk baseline.
