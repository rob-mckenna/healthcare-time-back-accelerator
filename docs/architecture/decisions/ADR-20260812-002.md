# ADR-20260812-002 — Correlation identifier format and single minting authority

**Status:** Accepted

**Owner:** Trinity

**Requirement IDs:** REQ-AUD-001, REQ-AUD-004, REQ-AGT-005

## Context

The charter requires one correlation identifier spanning request, generation,
decision, and evidence. The design review produced three incompatible proposals:
a bare 32-character hexadecimal string, a UUIDv4, and a date-prefixed
hexadecimal string. Each component in the path can mint identifiers, so without
a single authority the run fragments and the audit trail cannot be reassembled.

A correlation identifier is also the value most likely to end up in a log line,
an error message, and a screenshot. Anything it encodes leaks with it.

## Decision

The format is `CORR-YYYYMMDD-<32 lowercase hexadecimal characters>`, matching
`^CORR-\d{8}-[0-9a-f]{32}$`, always 46 characters.

The care-team experience layer mints exactly one identifier per run. Every other
component receives it and echoes it byte for byte. A component that emits a
different value than it received is a fail-closed condition, not a warning.

A bounded revision loop stays within one run and keeps one correlation
identifier; each generation attempt carries its own `generationId` and each
decision its own `approvalId`.

The user-visible short reference is the final eight hexadecimal characters, for
conversation only. It is never a lookup key and never stored as the correlation
value.

The hexadecimal segment must come from a cryptographically strong random source
and must never be derived from patient, encounter, user, tenant, or organization
values.

## Alternatives

- **Bare 32-character hexadecimal.** Rejected. Indistinguishable from a hash, a
  digest, or a token at a glance, which invites the wrong handling.
- **UUIDv4.** Rejected. Well supported, but carries no human-readable bracket,
  and its hyphenation is easily confused with the other identifier families in
  this repository.
- **Composite key such as `patientId + timestamp`.** Rejected outright. It
  encodes subject identity into a value designed to travel into logs.
- **Allow any component to mint when the value is absent.** Rejected. Silent
  minting turns a propagation bug into two unlinked audit trails that both look
  complete.

## Consequences

- Audit evidence for a run is retrievable with a single exact-match query.
- Runs can be partitioned by day without parsing payloads.
- The experience layer takes on a responsibility it cannot delegate, including
  during error paths, which the fail-closed catalog must cover.
- Format changes are expensive because the value appears in five contracts.

## Healthcare, privacy, security, and data impact

Positive. The identifier is deliberately content-free, so it can appear in logs,
on screen, and in support conversations without disclosing anything about a
subject. The date segment reveals only that a run occurred on a date, which is
already implied by the evidence record it labels.

## Validation evidence

`node scripts/validate-contracts.mjs` — the `correlation-propagation`
cross-field rule asserts that the agent input, agent output provenance, approval
event, audit event, and illustrative metric examples all carry an identical
correlation identifier. Pattern enforcement is compiled into
`contracts/schemas/common/definitions.schema.json#/$defs/correlationId` and
applied by every contract that references it.

## Supersedes
